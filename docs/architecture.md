# 架构说明

## 目标

这个项目优先保证内容可持续维护、身份边界清晰、发布失败可恢复，而不是追求复杂的后台系统。

## 分层

1. `content/`：项目、文章、资料和个人设置。
2. `scripts/content-schema.mjs`：内容契约和输入校验。
3. `app/`：页面、组件、响应式设计和内容呈现。
4. `.pages.yml`：非技术编辑者使用的可视化编辑界面。
5. `.github/workflows/`：质量检查与自动发布。

## 决策

### Git 文件代替数据库

当前内容规模不需要数据库。使用结构化 JSON 文件可以获得版本历史、回滚、可迁移性和低运维成本。

### 静态发布

每次内容更新后重新生成静态页面。访问者不依赖运行中的数据库或应用服务器，页面加载稳定，攻击面更小。

### 单一内容源

只编辑 `content/`。构建时生成的 `app/generated/content.ts` 不进入版本控制，避免维护两套内容。

### 资料库的双入口

资料条目通过 `entryType` 明确区分外部链接和站内文章。外部链接直接离站打开；站内文章复用统一阅读路由、Markdown 渲染、站点地图和 RSS，不维护第二套正文页面。

### 外部视频元数据

首页只保存两个经过域名校验的 B站视频链接。构建阶段通过固定的 B站接口读取标题和封面，展示层不保存重复字段；接口暂时不可用时降级为可跳转的占位卡片，不能阻塞整站发布。

### 受保护的长篇内容

GitHub Pages 没有服务端鉴权能力，不能把密码或长篇明文放入前端代码。长篇草稿保存在 Git 忽略的 `private-content/fiction/`，由本地脚本使用 PBKDF2-SHA-256 和 AES-256-GCM 加密。仓库与部署产物只保存 `public/protected/fiction/` 下的密文；浏览器在用户输入密码后解密目录和所选正文，密钥仅保留在页面内存中。

长篇入口不加入首页推荐、RSS 或 sitemap。加密只保护文字数据；引用 `public/` 下的图片仍可被直接访问。

### 隐私边界

内容 schema 不定义真实姓名、学号、班级、手机号或宿舍字段。隐私不是界面开关，而是数据模型约束。

## 质量门禁

- 内容 schema 校验
- TypeScript 类型检查
- ESLint
- 静态构建
- 主要路由渲染测试
- GitHub Pages 仅部署成功构建

## 恢复

所有内容更新都会形成 Git 提交。错误发布可以通过 GitHub 的 Revert 恢复，线上部署失败时则自动保留上一版本。
